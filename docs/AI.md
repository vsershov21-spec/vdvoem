# «Вдвоём» — как устроен ИИ: данные, обучение, ответы, отказы

Документ описывает, что реально работает в коде (ссылки на файлы), а что пока в плане. Метки: **[есть]** — в проде, **[в работе]** — пишется сейчас, **[план]** — не начато.

## 1. Главный принцип

**Модель понимает — сервер отвечает.**

Языковая модель (локальная qwen2.5 через Ollama, бесплатно) делает одно: переводит фразу человека в структуру `Intent` (что сделать и с какими фильтрами). Факты — цены, даты, места, кто играет, совпадение вкусов — берутся только из базы и подставляются в ответ шаблоном. Поэтому маленькая модель не может придумать цену или спектакль: в ответе нет места, куда она могла бы это написать.

Второй принцип: **ничего не меняется без нажатия.** Помощник предлагает кнопки («Идём», «Добавить», «Бюджет 5000 ₽»), действие выполняется только по нажатию, один раз (`assistant.Act`).

## 2. Путь одного запроса **[есть]**

```
фраза ─► правила (мгновенно, уверенность 0..1)
          │ уверенность ≥ 0.8 ─────────────────────────────┐
          ▼ иначе                                           │
        модель: JSON по схеме, бюджет 6.5 с                 │
          • системный промпт + 16 фиксированных примеров    │
            (префикс кэшируется Ollama)                     │
          • + 3 самых похожих «правильно понятых» запроса   │
          • ответ не уложился / ошибка → чтение правил      │
          ▼                                                 │
        sanitize: только известные значения полей ◄─────────┘
          ▼
        уточнение? («а подешевле», «а без театра») → склейка с прошлым Intent
          ▼
        исполнитель (do.go): данные → шаблон ответа + карточки + кнопки
          ▼
        лог: intent, источник (rules/model/fallback), мс; пример для обучения
```

Файлы: `internal/assistant/intent.go` (правила, схема, модель), `recall.go` (похожие примеры), `do.go` (исполнитель), `afisha.go` (поиск по афише и копилке).

Типы запросов (`intentNames`): `find` — поиск с фильтрами (день, часть дня, бюджет, категории, исключения, **настроение**, горизонт «на месяцы вперёд»); `suggest` — одна идея из копилки или «удиви»; `price`; `book` — записать событие в календарь; `remember`; `goal` — «следи за…»; `overview`; `past`; `chores`; `add_idea`; `budget`; `suggest_mode`; `plan`; `chat`. **[в работе]** `about` — «расскажи про…», «кто играет», «подойдёт ли нам».

Бюджет времени: правила ≈ 0 мс; модель ≤ 6.5 с (`LLMBudget`), дальше — ответ по правилам. Модель держится загруженной: прогрев каждые 4 минуты (`Warm`).

## 3. Когда ответа нет — лестница отказов **[есть]**

Помощник никогда не отвечает «не знаю» молча и никогда не выдумывает. По шагам:

| Ситуация | Что делает |
|---|---|
| Модель не успела / упала | Берёт чтение правил (`rules-fallback`), человек этого не замечает |
| Запрос непонятен (уверенность < 0.5, не приветствие) | «Не до конца понял» + примеры формулировок |
| По фильтрам ничего в афише скаута | Повторяет поиск по всей копилке |
| И там ничего | Показывает идеи того же настроения из встроенного каталога (40 видов свиданий) с кнопками «Добавить» |
| Искали конкретное («театр через 2 месяца») | Ставит вопрос скауту; ответ придёт в бот |
| Цена неизвестна | Данные → страница события (3.5 с) → вопрос скауту + ссылка «посмотреть самому» |
| Вещи нет вообще | Ссылка на поиск + вопрос скауту |
| Нельзя выполнить (нет пары, уже идёт выбор, у события нет времени) | Объясняет почему и предлагает путь: пригласить, завершить выбор, выбрать время |

## 4. Данные (датасеты)

Всё хранится в SQLite на сервере; картинки — только ссылки.

| Набор | Где | Что | Зачем |
|---|---|---|---|
| Идеи и события | `ideas` | название, категория, цена на двоих, даты, площадка, источник (`""` человек / `scout` / `channel`), горизонт, «почему», **[в работе]** `info`: описание, жанры, состав, возраст, источник фактов | всё, о чём говорит помощник |
| Отметки | `ideas.wish_a/wish_b`, `again_*`, итоги встреч | хочу / очень / пропущу / «повторим?» у каждого | обучение вкуса каждого |
| Слова людей | `memories` | «я не ем морепродукты», «не люблю стендап» — у каждого своё | помощник и скаут учитывают |
| Цели | `scout_goals` | «следи за Земфирой» | скаут ищет на месяцы вперёд |
| Вопросы | `scout_questions` | то, на что у приложения не было ответа | скаут отвечает в бот |
| Примеры понимания | `llm_examples` | фраза → Intent (JSON) → ответ; `accepted`, если нажали кнопку из ответа | живой датасет: recall и дообучение |
| Золотой набор | `intent_eval.go` | 103 размеченных запроса + 30 отложенных (правила под них не настраивались) | проверка качества и скорости |
| Посты каналов | через бота / выгрузку | пересланные посты и выгрузки каналов | события со скидочными билетами |

Доверие к фактам: пост канала или страница события (дословно) > находка скаута со ссылкой > слова человека о себе. Факт без источника не сохраняется.

Приватность: у каждой пары своё пространство, у каждого человека своя модель вкуса и своя память — архитектура готова к продаже многим парам. Скауту уходят брифы без имён; служебные входы `/agent/*` отвечают только изнутри сервера.

## 5. Обучение — три контура

### 5.1 Вкус каждого человека **[есть]** — `internal/taste`

- Модель: логистическая регрессия на признаках идеи: категория, ценовой диапазон, будни/выходные, время суток, слова названия (с отсечением окончаний), источник, настроения (`tag:`); **[в работе]** жанры (`g:`) и площадка (`v:`).
- Данные: отметки этого человека («очень» весит 2, «пропущу» — отрицательный пример).
- Обучается заново на каждом запросе (микросекунды): модель всегда равна текущим отметкам, без дрейфа, ничего не хранится.
- До 10 отметок оценка стягивается к 50%: две отметки ещё не дают уверенности.
- Пара: `0.65·min + 0.35·max` — вариант, который устраивает обоих, выше любимого варианта одного.
- Объяснимость: `Explain` даёт «любит / не любит» на экране «Мы»; **[в работе]** `Reasons` — почему конкретное событие подходит или нет.

### 5.2 Понимание запросов

- **[есть] Правила** — словари и регулярные выражения для ясных запросов: 102 из 103 золотых, 13 из 30 отложенных. Отложенные показывают честную обобщающую способность правил; остальное — работа модели.
- **[есть] Recall — обучение без переобучения.** Перед вопросом модель видит 3 самых похожих запроса из золотого набора и подтверждённых живых запросов (нажали кнопку — значит поняли правильно). Чем больше пара пользуется, тем точнее модель, без GPU.
- **[есть] Оценка:** `vdvoem eval <модели>` прогоняет правила, модель и связку на 133 запросах: точность, среднее, p90, худшее время, список ошибок.
- **[есть] Датасет и дообучение LoRA** (`deploy/train`): генератор даёт 2300 + 300 + 250 размеченных запросов (разметка верна по построению; в test — шаблоны и названия, которых нет в обучении). Ноутбук Colab (бесплатный GPU T4, ~30–40 мин) обучает адаптер к Qwen2.5-3B и сам кладёт его в релиз `lora`. `install-lora.sh` на сервере без root собирает `vdvoem-intent`, проверяет старую и новую модель на отложенных запросах и включает новую, только если она лучше на 3+ п.п., p90 ≤ 6.5 с и не хуже на золотом наборе. Дообученная модель получает короткий промпт без примеров — так она и быстрее. Правила на test датасета: 34% — это нижняя планка, от которой меряем.

### 5.3 Знания о событиях

Модель ничего не «знает» о спектаклях сама: знания лежат в базе и пополняются из источников.

- **[есть] Скаут** (агент Claude, раз в неделю): ищет события по вкусам каждого в 10+ источниках (KudaGo, Яндекс Афиша, afisha.ru, Timepad, Ticketland, kassir, MTS Live, culture.ru, сайты театров), перепроверяет цены, отвечает на вопросы. Только факты со ссылкой.
- **[есть] Посты каналов**: детерминированный разборщик афишного формата («🔴 НАЗВАНИЕ … 19 ноября 19.00 … 🔥4500 вместо 5500»). Модель — только запасной путь для нестандартных постов, и каждое её поле сверяется с текстом поста: нет в тексте — поле выбрасывается.
- **[в работе] Жанры, описание, состав, возраст**: словарь жанров (комедия, драма, мюзикл, оперетта, классика, иммерсивный, детям, джаз…), «В ролях:», «12+», первый абзац описания. Скаут заполняет то же из интернета для каждой находки и перепроверяемых событий.

## 6. Как помощник рассказывает о событии **[в работе]**

«Расскажи про Чайку», «кто там играет», «подойдёт ли нам»:

1. Найти событие по названию в афише и копилке.
2. Факты из `info` и полей события: площадка, даты, цена (и обычная цена, если скидка), жанры, возраст, состав, 1–3 предложения описания — дословно из источника.
3. Подойдёт ли: процент для каждого и для пары по их моделям вкуса, плюс причины из `Reasons` («тебе: любишь драму, МХТ; Насте: сомнительно — не любит длинные спектакли»), плюс их собственные слова из памяти, если касаются события.
4. Нет описания → «подробностей пока нет», вопрос скауту, ссылка.

## 7. Защиты

- Ответ модели — данные, не текст: схема JSON (грамматика Ollama) + `sanitize` (только известные значения).
- Сверка с источником для всего, что извлечено из текста.
- Лимит: 40 вопросов на человека в день.
- Кнопки одноразовые и срабатывают только по нажатию.
- Ни имён, ни токенов в брифах скаута; `/agent/*` только с самого сервера.

## 8. Что не сделано и риски

- **Живых данных мало.** Модели вкуса включаются примерно после 10 отметок у каждого. Пока отметок нет, решают рейтинг скаута и настроение.
- **Модель на CPU медленная.** Длинный пост канала она читает 1–2 минуты и в это время занимает модель; помощник тогда отвечает по правилам. Поэтому для постов основной путь детерминированный.
- **LoRA не обучалась** (см. 5.2): нужен GPU и несколько сотен подтверждённых примеров.
- **Ежедневные ответы скаута**: сейчас скаут отвечает на вопросы раз в неделю; задача «два раза в день» не создана — нужно разрешение.
- **Контент каналов** чужой: для продажи приложения другим парам нужно согласие автора канала или партнёрство.
